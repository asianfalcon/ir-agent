# 🤖 金融投研分析智能体系统 (IRA) 产品需求文档 (PRD)

## 1. 项目概述 (Project Overview)

### 1.1 系统定位

本项目旨在打造一个全链路的金融投研分析智能体系统 (IRA)。系统通过“三方API自动抓取 + 本地文件监听 + 网络爬虫”双轨机制汇聚多源异构数据，利用混合检索增强 (Hybrid RAG) 与智能体对抗网络，在本地环境下，自动实现上市公司的全方位追踪、数据交叉比对，。

### 1.2 核心痛点与系统目标（“六性”质量约束框架）

系统在架构设计与代码落地上面临多重复杂的量化投研痛点。为确保系统输出的结论具备实战参考价值，系统底座及智能体运行期必须严格死守以下六大质量约束指标：

| ❌ 核心痛点 | 🎯 系统目标 | ⚙️ “六性”质量约束与工程落地支撑 |
| --- | --- | --- |
| **时序财务幻觉与定量断层**<br>

<br>大模型易混淆历史季度数字；财务指标零散，依赖手动 Excel 拼凑。 | **100% 确定性因子计算**<br>

### 1.4 全链路数据血缘设计规范（可追溯性落地）

为了确保最终输出的每一份投研报告在量化层面上绝对合规且可被审计，系统在数据流转的每个节点都必须严格维护数据血缘（Data Lineage）：

* **源头打标：** 当 `Watchdog` 或 `Spiders` 捕获到原始文件并写入 `data/raw/` 时，必须同步在 SQLite 系统的 `sys_data_lineage` 表中注册该文件的唯一全局 ID（`source_id = MD5(file_path)`），记录其下载源、访问权限及时间戳。
* **加工传递：** 文本经过提纯转换后，无论是在 SQLite 中生成的财务记录，还是在 LanceDB 中生成的向量 Chunk，其元数据（Metadata）中必须强制附带 `source_id`。如果是 PDF 文件，必须通过正则匹配物理页码，将 `page_num` 作为强硬字段一并写入。
* **推理渲染：** 当 Skill 4（多源对抗互证器） 拼凑出结论时，必须从底层数据库的 `source_id` 中反向解析出原始文件的文件名及网页链接，并强制使用标准的 `[^1]` 脚注形式，在报告中进行级联展示。

## 2. 采集输入层需求 (Data Ingestion Module)

### 2.1 本地文件监听器 (Local File Watchdog)

* **监控目标：** 实时监控 `data/inputs/reports/` (研报) 和 `data/inputs/announcements/` (公告) 两个物理文件夹。
* **高可用异常边界：**
* **文件锁延迟锁定：** 用户拖入大文件（如 50MB 研报 PDF）时会触发连续的 `modified` 事件。系统必须在监听到事件后延迟 2 秒，确认文件大小不再变化且文件流可独占读取时，方可将文件压入后台任务队列。
* **崩溃重扫机制：** 每次启动时，系统需比对物理文件夹内文件的 `mtime` (修改时间) 与本地 SQLite `sys_file_log` 表中的记录，对未处理或修改过的新文件进行增量补扫。



### 2.2 三方 API 定时调度器 (API Scheduler)

* **调度引擎：** 使用 `APScheduler` 留驻后台。
* **行情流：** 每个交易日 15:30，调用 AkShare 获取指定自选股池的当日日线行情与主力资金流向，落盘为 `data/raw/market/{date}_{ticker}.json`。
* **财报流：** 财报季（A股 4月、8月、10月），每晚 22:00 增量请求最新的财务核心指标快照，落盘为 `data/raw/financials/{ticker}_{period}.json`。
* **缓存拦截约束：** 发起 API 请求前，强制检索本地对应路径，若今日快照已存在，直接拦截请求并读取本地 Raw 快照。

### 2.3 网络定向爬虫引擎 (Web Spiders)

* **技术栈：** Playwright 异步无头模式。
* **增量去重逻辑：** 爬虫启动后先抓取目标网站（如生意社商品页）的 HTML 列表，提取各条目的 URL。将 `URL + 当前日期` 进行 MD5 加密，比对 SQLite 中的 `spider_crawl_log` 表。若命中主键冲突则直接跳过该条目，只向下爬取增量页面。

## 3. 加工提纯层需求 (Data Processing & Transformation)

### 3.1 核心变量字典与实体词库结构定义

配置文件严格以 JSON 格式持久化存储于 `config/` 目录下。

* **实体词库 (`config/vocab_dictionary.json`)**

```json
[
  {
    "standard_name": "钛白粉",
    "entity_type": "Product",
    "aliases": ["二氧化钛", "TiO2", "金红石型钛白粉", "锐钛型钛白粉"]
  }
]

```

* **变量字典 (`config/variable_schema.json`)**

```json
[
  {
    "var_name": "gross_margin",
    "data_type": "Float",
    "source_field_mapping": ["销售毛利率", "毛利率", "Gross Profit Margin"],
    "rounding_precision": 4
  }
]

```

### 3.2 异构文本解析与去噪清洗规则

* **PDF 研报过滤算法：** 使用 PyMuPDF 提取文本。必须编写正则过滤器清除以下两类噪声：
* **页眉页脚去噪：** 匹配每页首尾两行的“请务必阅读正文之后的免责条款”、“Page X”、“证券研究报告”及页码数字。
* **免责声明截断：** 一旦文本中匹配到“### 免责声明”或“投资评级说明”等标志性字样，立即放弃后续所有文本的提取。


* **HTML 智能清洗：** 使用 BeautifulSoup 配合 Readability 核心节点识别算法，强制剥离 `div.nav`、`div.footer`、`script`、`style` 标签，仅保留 `h1`, `h2`, `h3`, `p` 和 `table` 元素。

### 3.3 语义切片与元数据硬注入规范

* **切片参数：** 采用 `RecursiveCharacterTextSplitter`。`chunk_size=700` 字，`chunk_overlap=70` 字。
* **元数据注入：** 每一个文本 Chunk 必须作为一个标准字典对象传递给向量库，其数据结构规范为：

```python
{
    "chunk_id": "md5_string_of_text",
    "text": "本季度安纳达钛白粉产能全开，毛利率提升至...",
    "metadata": {
        "ticker": "002136.SZ",               # 必须标准化
        "pub_date": "2026-06-29",            # 严格的时效依据
        "period": "2026Q2",                  # 时序硬过滤核心
        "associated_vars": ["gross_margin"], # 关联的变量字典字段
        "data_source": "broker_report"       # 枚举: broker_report / announcement / web_news
    }
}

```

## 4. 多模态存储层需求 (Multi-Modal Storage Grid)

本系统采用嵌入式、无服务器的轻量级存储底座。

### 4.1 SQLite 表结构设计 (定量“死数字”底座)

必须在系统初始化时建立以下核心表结构：

```sql
-- 企业基本信息表
CREATE TABLE IF NOT EXISTS companies (
    ticker TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    sector TEXT
);

-- 标准财务时序表
CREATE TABLE IF NOT EXISTS financial_reports (
    ticker_period TEXT PRIMARY KEY, -- 复合主键规则: ticker + "_" + period (如 "002136.SZ_2026Q2")
    ticker TEXT NOT NULL,
    period TEXT NOT NULL,           -- 格式规范: YYYYQ1 / YYYYQ2 / YYYYQ3 / YYYYQ4
    gross_margin REAL,              -- 数值类型，Float/Real
    net_profit REAL,
    roe REAL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY(ticker) REFERENCES companies(ticker)
);

-- 商品/股票价格时序表
CREATE TABLE IF NOT EXISTS historical_prices (
    item_code TEXT NOT NULL,        -- Ticker 或 商品简称
    price_date TEXT NOT NULL,       -- 格式: YYYY-MM-DD
    price_value REAL NOT NULL,
    PRIMARY KEY (item_code, price_date)
);

```

### 4.2 LanceDB 向量存储与索引设计 (定性“证据链”仓库)

* **表初始化：** 在本地创建名为 `data/storage/lancedb_root` 的物理目录。
* **索引构建：** 当单张表的文本 Chunk 数量达到 10,000 条以上时，系统需自动触发构建 IVF-PQ 混合索引（聚类中心数设定为 `num_partitions=256`，子向量数设定为 `num_sub_vectors=96`），确保单次混合向量检索响应延迟在 150 毫秒以内。

### 4.3 Kùzu 图数据库设计 (产业链“常识与因果”图谱)

基于嵌入式图数据库 Kùzu 进行本地常驻。

* **图 Schema 拓扑定义：**

```cypher
// 1. 创建节点表
CREATE NODE TABLE Company(ticker STRING, name STRING, PRIMARY KEY(ticker));
CREATE NODE TABLE Product(name STRING, PRIMARY KEY(name));

// 2. 创建关系表
CREATE REL TABLE PRODUCES(FROM Company TO Product);
CREATE REL TABLE UPSTREAM_OF(FROM Product TO Product, transmission_coefficient FLOAT);

```

### 5.1 Skill 1: Text2SQL 确定性提取器

* **输入参数：** 投资经理的自然语言提问。
* **执行边界：**
1. 系统提取提问中的公司名，查阅词库对齐为标准 Ticker。
2. 将 `variable_schema.json` 中的字段说明组装进 Prompt 的 Context 中，强制约束大模型只能使用 Schema 中定义过的列名生成 SQL 语句。
3. 执行完 SQL 后，将结果集直接透传给后端，大模型严禁擅自修改查询出来的数字。



### 5.2 Skill 2: 确定性财务公式计算器

* **核心逻辑：** 专门处理同比（YoY）、环比（QoQ）以及行业均值横向对标。
* **执行规范：** 由后端 Python 逻辑根据 SQLite 捞出的原生成绩进行纯数学运算，公式固化在代码中。

$$\text{毛利率变动弹性} = \frac{\Delta \text{gross\_margin}}{\Delta \text{upstream\_price}}$$



### 5.3 Skill 3: 产业链路径传导器

* **核心逻辑：** 当输入某一具体商品或行业变量时，自动触发图查询。
* **Cypher 传导语句模板：**

```cypher
MATCH (p1:Product {name: $input_product})-[r:UPSTREAM_OF]->(p2:Product)<-[:PRODUCES]-(c:Company)
RETURN c.name, c.ticker, p2.name;

```

该组件直接输出受原材料价格波动波及的上市公司目标池。

### 5.4 Skill 4: 多源对抗互证器 (佐证核心组件)

本系统的最核心“质检天平”。此 Tool 负责收集前述 Skills 捞出的多异构通道数据，强制大模型按照以下 System Prompt 进行矛盾点与冲突点挖掘：

```plaintext
[System Prompt: Multi-Source Adversarial Verifier]
你是一个严苛的投研风控专家。请将以下三组数据放在天平两端进行比对：
1. 官方表述 (SQLite财务数据与公告文本)
2. 卖方预期 (券商研报向量切片)
3. 客观现实 (垂直行业网站抓取的实时商品价格与供需舆情)

请执行以下辩证对齐动作：
- 检查【官方自述】的毛利率趋势是否与【客观现实】的原材料涨价周期相冲突？
- 检查【卖方预期】给出的盈利预测，是否显著脱离了【官方自述】的历史时序连续性？
- 必须找出至少一个潜在的矛盾点（如：产品高位滞涨 vs 研报强烈推荐产能消化），若无显著冲突，需提示信息链的完整性风险。

```

## 6. 表现生成与用户交互需求 (Presentation & Interface)
